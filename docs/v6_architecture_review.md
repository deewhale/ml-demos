# V6 架构复盘

> 2026-04-12 | 项目从 V3 到 V6 的完整演进回顾，问题诊断，以及下一步方向讨论。

---

## 一、项目演进

### V3: DQN 基线（2026-04-03）

**核心思路**：卡牌游戏的强度来自组合。用 Self-Attention 编码牌组+遗物的配合关系（DeckEncoder），输出"牌组 DNA"向量，作为所有下游决策的共享上下文。战斗用 DQN，选卡/选路用局末监督训练。

**架构**：
- DeckEncoder（Self-Attention）→ 32 维 deck DNA
- CombatNet（DQN）：战场状态 356 维 → 4 层 MLP → 11 个动作 Q 值
- CardPickNet / PathNet：deck DNA + 上下文 → 价值分
- 从 759 个历史 .run 文件预训练选卡网络

**结果**：34 局训练，A20 下平均 floor 7-12，出现退化。A0 未测。

**解决了什么**：
- 建立了完整的 Communication Mod 对接管线
- 验证了 DeckEncoder 的可行性
- 建立了 bloom filter hash 编码体系

**遗留问题**：
1. DQN 不适合序列动作问题——每回合多次出牌，DQN 把每次出牌当独立决策
2. 无跨局信用分配——选卡/选路只有局末一个标量信号
3. Replay buffer 重置导致灾难性遗忘
4. 硬编码目标选择（打最低 HP 怪）

---

### V4: PPO + Shared Transformer（2026-04-04）

**核心思路**：用 PPO 替代 DQN，用 Shared Transformer 统一所有决策头。Autoregressive combat head 支持出牌+选目标的序列决策。共享编码器让所有决策类型的梯度都能改善表征。

**架构**：
- Context Transformer（2 层 4 头，dim=64）→ 128 维 shared_repr
- 4 个 head：Combat（autoregressive）/ Draft / Path / Choice
- 每个 head 独立 value function
- PPO 训练，γ=0.999，~650 transitions/run

**结果**：557 局训练（A0），平均 floor 9.0，0 胜。后续扩展到 2748 局，平均 floor 4.2（注：后期数据可能包含调参导致的退化）。

**解决了什么**：
- PPO 解决了 DQN 的探索/利用问题
- Autoregressive combat head 支持了出牌+选目标
- 共享编码器让不同决策类型互相增强
- 建立了 PPO + GAE 训练流水线

**遗留问题**：
1. 编码信息不足——agent 看不到敌人意图细节、卡牌效果语义、具体 buff/debuff
2. 奖励是 if-else 启发式——硬编码了战术偏好（block efficiency、debuff value 等），封顶了学习上限
3. 模型太小（152K 参数）
4. deck_profile 是 bloom hash 统计指纹，丢失了具体牌的信息

---

### V5: TurnSolver 接管 Combat（2026-04-06 ~ 04-10）

**核心思路**：combat 太难用 RL 学，让搜索树 Solver 接管所有战斗决策。Agent（Transformer + PPO）只处理策略层：draft（选牌）/ path（选路）/ choice（事件/休息/商店）。每局约 50 个策略决策，RL 难度大幅降低。

**架构**：
- TurnSolver 处理所有 combat 决策（搜索树，按房间类型分配算力）
- Agent 只训练 3 个策略 head：Draft / Path / Choice
- Combat head 保留但冻结，作为退路
- γ=0.99（策略层 episode 只有 ~50 步）
- 逐卡 token + 可学习 ID 嵌入（22-dim 数值特征 + 16-dim ID embedding = 38-dim）

**解决了什么**：
- 战斗质量大幅提升（Solver 搜索树比随机 RL 强得多）
- 策略层决策数量从 ~650 降到 ~50，RL 更容易收敛
- 编码层大幅完善：升级/删牌接入 draft head，商店决策，Neow 祝福，事件编码优化，遗物编码

**遗留问题**：
1. Solver 是外部依赖，不是模型自己的能力
2. 用户核心诉求："combat 是学习卡牌的课堂"——如果不打牌，怎么理解牌的价值？
3. 编码层仍然有信息缺失——卡牌效果的核心语义（抽牌、中毒、虚弱等）没有结构化编码，baseMagicNumber 多义未拆分
4. 可学习 ID 嵌入需要大量训练数据才能收敛（256 × 16 = 4096 参数），训练量不够时等于噪声

---

### V6: 统一效果编码 + Agent 全决策（2026-04-11 ~ 04-12）

**核心思路**：两个关键改变：
1. **编码层重写**——从 StSRLSolver 的 cards.py/relics.py/potions.py 静态查表，卡牌/遗物/药水统一为 ~57 维效果向量（damage, block, draw, energy, poison, vulnerable, weak, strength, dexterity 等全部结构化）
2. **Agent 自己打牌**——不外包给 Solver，combat 是模型学习卡牌机制的课堂

**设计决策**：
- 同一编码跨场景共享：手牌、选牌奖励、牌组里的卡用完全相同的编码
- 不用 ID embedding 和 hash：模型完全靠效果特征理解实体
- 角色差异只是初始遗物不同，模型学通用策略能力
- Power 编码改为 ~20 功能类别，每类 2 维 → 44 维

**架构**：
- Context Transformer（3 层 4 头，dim=128）→ 256 维 shared_repr
- 4 个 head：Combat（autoregressive）/ Draft / Path / Choice
- PPO 训练，γ=0.999，per-card immediate reward
- 多进程训练（4 workers），16 games/batch

## 三、核心问题

### 3.1 防卡死机制主导了战斗

训练日志显示，大量回合的结束并非模型主动选择 END_TURN，而是防卡死机制（`_stuck > 3 or _screen_repeat > 10`）触发的强制推进。模型在战斗中没有学会基本的出牌→结束回合循环，而是反复选择无效动作直到被强制跳过。

这意味着模型从战斗中获得的 reward 信号几乎是噪声——不是"我选了 A 得到了 R"，而是"我选了很多无效动作，然后被强制跳过了"。

### 3.2 从零学 combat 效率极低

RL 从零开始学 STS combat 的难点：

- **状态空间巨大**：几百张不同卡牌 × 多种敌人 × buff/debuff 组合 × 能量/手牌变化
- **信用分配困难**：出牌 → 回合结束 → 敌人行动 → HP 变化，因果链跨越多步
- **动作空间复杂**：每回合要做 3-5 个出牌决策，每个决策 11 个选项 × 4 个目标
- **即使有 per-card reward**，模型仍然学不会"先打有 Vulnerable 的怪"或"能量不够时结束回合"等基础策略

### 3.3 缺少 combat 学习数据

人类 .run 数据（800+ 局）只包含策略层决策（选牌、选路、篝火、事件），**完全没有 combat 出牌记录**。这意味着：

- 行为克隆（Behavior Cloning）对 combat 不可用
- 预训练只能覆盖策略层
- Combat 能力必须完全从 RL 探索中获得

## 四、为什么用 RL？——待讨论

### 选择 RL 的历史原因

项目从 demo1（MNIST 监督学习）→ demo2（CartPole DQN）→ demo3（STS agent）自然演进。CartPole 用 DQN 几百局就学会了，STS 看起来是"更复杂的 CartPole"，所以自然选择了 RL。

### RL 的理论假设

RL 的核心假设是：agent 通过与环境交互，根据 reward 信号自主学习最优策略。这个假设在以下条件下效果好：
- 状态空间可控（CartPole: 4 维连续状态）
- 动作空间小（CartPole: 2 个动作）
- 因果链短（CartPole: 动作 → 立即看到效果）
- 单一目标（CartPole: 不倒就行）

### STS 为什么难

STS 几乎违反了上述所有条件：
- **状态空间**：手牌组合 × 敌人状态 × buff/debuff × 能量 × 牌组状态，有效状态空间极大
- **动作空间**：每回合 3-5 次出牌决策，每次 11 × 4 = 44 种组合
- **因果链**：出牌 → 回合结束 → 敌人行动 → HP 变化 → 下一回合，因果链长且有随机性（抽牌、敌人行为）
- **多目标**：构建牌组（长期）+ 管理 HP（中期）+ 赢得当前战斗（短期）

**500 局够吗？** 用户认为好的设计应该很快见效，不应该需要海量训练。AlphaGo 虽然需要百万局，但它的每一局都能完整走完并获得明确的胜负信号。STS 的 500 局中，模型连"出一张攻击牌打怪"这个基本动作都没学会。问题不在训练量，在于模型根本没有从 reward 信号中学到有意义的行为。

## 五、可能的替代方案（待讨论）

以下列出可能的方向，不做结论，留给讨论。

### 1. 行为克隆（Behavior Cloning）

从人类数据学策略。

- **优势**：直接从好的决策中学习，不需要探索
- **问题**：缺少 combat 出牌数据（.run 文件没有），只能覆盖策略层
- **可能的数据源**：如果能录制人类的 combat 操作（需要 mod 支持），就有训练数据

### 2. 搜索/规划（MCTS / Solver）

V5 的 TurnSolver 方向——用搜索树找最优出牌序列。

- **优势**：不需要训练，搜索树直接给出好的 combat 决策
- **问题**：用户认为模型应该自己学，Solver 是"作弊"
- **折中**：Solver 作为教师——用 Solver 生成 combat 训练数据，agent 从中学习

### 3. 混合方案：预训练 + 微调

- 策略层用 .run 数据行为克隆预训练（已有 pretrain_v5.py）
- Combat 层用 Solver 生成数据预训练
- 然后用 RL 在线微调
- **优势**：不从零开始，RL 只需学增量改进
- **问题**：Solver 生成的数据可能有系统性偏差

### 4. 基于规则的启发式

手写 combat 策略（"有 Vulnerable 先打 Vulnerable 的怪"、"挡不住就全防"）。

- **优势**：立即生效，可以很强
- **问题**：用户明确不想硬编码游戏知识，项目目标是让 AI 自主学习

### 5. 模型预测（World Model）

学习状态转移模型（"打出 Strike 后世界会变成什么样"），然后在"想象"中训练。

- **优势**：一次真实交互可以产生多次"想象中的训练"，数据效率高
- **问题**：STS 的状态转移复杂（卡牌效果多样），学习准确的 world model 本身就是一个难题
- **参考**：Dreamer / MuZero 用这种方法在 Atari 上取得了好结果

### 6. Solver 作为教师（DAgger / 蒸馏）

TurnSolver 每回合搜索最优解，把（状态, 最优动作）对作为监督信号训练 agent。

- **优势**：combat 数据无限量，质量由 Solver 保证
- **问题**：模型学到的上限是 Solver 的水平；但如果 Solver 足够强，这不是问题
- **与用户诉求的关系**：模型确实"自己学了"（从数据中学），只是数据来源不是自我探索而是教师演示

### 7. Curriculum Learning（课程学习）

不从完整游戏开始，而是从简单场景逐步升级。

- **优势**：模型先学会"出 Strike 打怪"，再学"怎么搭配出牌"，再学"怎么构建牌组"
- **实现**：可以用 StSRLSolver 构造简化场景（只有 Strike+Defend 的 deck，只打 Cultist）
- **问题**：需要手动设计课程，课程之间的迁移不一定顺畅

### 8. 其他可能

- **离线 RL（如 CQL/IQL）**：从 Solver 生成的数据离线训练，不需要在线交互
- **进化策略（ES）**：不用梯度，用群体搜索——对 STS 这种稀疏奖励问题可能更鲁棒
- **LLM 辅助**：用大语言模型生成 combat 策略的文本描述，编码为规则

## 六、用户的核心诉求（整理）

从项目历程和讨论中提炼的关键原则：

1. **模型不能是瞎子，特征要完整** — V6 已解决（统一效果编码 57 维）
2. **好的策略应该很快见效** — 不应该需要海量训练才能看到基本能力
3. **不要人工打标签，模型自己学** — 排斥硬编码的游戏知识和手写规则
4. **角色间的知识应该通用** — V6 已解决（统一编码，角色差异只是初始遗物）
5. **Combat 是学习卡牌的课堂** — 不打牌就不可能理解牌的价值，Solver 接管 combat 违背这一点
6. **不需要完美，但要比盲打明显好** — 6.1 的平均 floor 和盲打差不多，这不可接受
7. **诊断优先级**：表征/架构/奖励 > 算法 > 训练量 — 不能用"训练量不够"搪塞

## 七、下一步讨论要点

V6 证明了两件事：
- 编码层终于完整了（统一效果编码，模型不再是瞎子）
- 纯 RL 从零学 combat 在当前训练效率下走不通（500 局无学习趋势）

核心矛盾是：**用户希望模型自己学 combat，但纯 RL 的探索效率太低**。

需要讨论的关键问题：

1. **"自己学"的边界在哪里？** Solver 生成训练数据算不算"自己学"？如果一个人看教学视频学下棋，算不算"自己学"？
2. **如果坚持纯 RL，需要什么改变？** Curriculum？更好的 reward shaping？更长的训练？
3. **如果接受"教师"，哪种形式最可接受？** DAgger（Solver 示范）？行为克隆预训练 + RL 微调？
4. **500 局的诊断还缺什么？** 是否需要更细粒度的分析（哪些类型的战斗死的最多？模型的出牌分布是什么样的？）

这些问题没有标准答案，取决于项目目标是"做出一个能赢的 AI"还是"探索 RL 在复杂游戏中的能力边界"。
