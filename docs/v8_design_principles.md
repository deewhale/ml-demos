## Claude 复述（用户已确认理解对）

### 1. 路线（MAP）

**评估依据**：综合 "已有战损" + "牌组强度"

**好路线应该做的**：
- 牌组强度不够 → 多走 monster（补卡）
- 有关键卡 / HP 低 → 走 ? / rest（敲牌 / 回血）
- 不是只看眼前一步，要**预期** + **规划整条路线** + 根据当前状态**实时调整**

**关键词**：路线评估不是单步决策，是 long-term planning。需要"战损 + 牌组强度"两个维度作为评估输入。

### 2. 战斗内（深度搜索 + 模型）

model 要学的具体能力：
- 怎么打牌**伤害最高**
- 哪些卡有**联动**（例：先痛击再打击=17，先打击再痛击=14——出牌**顺序**影响伤害）
- **战损最低**（防御）
- 先打哪只小怪战损最低（**target 选择**）

**关键词**：出牌顺序、联动、target 选择——都是搜索能枚举的，model 学搜索的输出。

### 3. 选卡（CARD_REWARDS）+ 战斗后评估

每场战斗后对卡组做综合评分，多个维度：
- 哪些卡**输出最多**
- 哪些卡能**有效阻止伤害**
- **运转卡能不能抽出核心卡**（drawing 卡的价值）
- **加费卡能多打出核心卡**（energy 卡的价值）
- **能力牌的提升有多少**（power 卡的价值）

是在**战斗之后**做的 check。model 通过这些**评分反馈**学到怎么选卡。

## 核心原则

**不是 RL 黑盒一个 `game_won` 信号反推所有，是分层评估，每个子决策有自己的"懂行"信号：**

| 子决策 | 评估机制 |
|---|---|
| 路线 | 战损 + 牌组强度 |
| 战斗内 | 伤害 / 战损 / 卡联动顺序 / target 选择 |
| 选卡 | post-battle 牌组多维评分（输出 / 防御 / draw / energy / power 各自分数）|

## 工作方法论（用户教的协作原则）

### 1. 角色分工

- **用户的责任**：防止 Claude 跑偏（验证设计 / 提醒原话 / 纠错方向）
- **Claude 的责任**：按稳定的工程化方式持续推进，不焦虑不绝望
- **技术选型 Claude 做主**（用户不懂 ML 术语，Claude 是专家），但**设计意图用户定**
- 用户原话："你的责任是按照稳定的工程化方式持续推进，我的责任是保证你不跑偏"

### 2. 严格的工程化方法论

任何方案必须按下面顺序走：

1. **现在是什么困难导致成绩不好**（根因分析，不要笼统）
2. **怎么解决**（针对根因，不是泛泛）
3. **这些方案能不能解决问题**（自检，不强凑）
4. **每个方案对应解决哪些具体问题**（一一对应表）

不能跳步骤直接提方案。**自检发现方案不解决问题就 stop，不强行推进**。

### 3. 颗粒度

- 不要"大粒度"方案（如"训新 model"、"调参 sweep"、"换评分函数"）
- **拆到具体子决策**（路线 / 选卡 / 战斗内 / 事件 / 商店 / 休息）
- 找出**哪个具体子决策出错**，针对性解决
- 用户原话："你的颗粒度太粗来，现在是选卡不行，路线不行，还是战斗内打的都不行？"

### 4. 不能随便提方案让用户拍

- **禁止"丢三选一让用户选"**（用户讨厌这种甩锅）
- 给一个明确推荐 + 理由 + 让用户判断
- 自己拿不定时直说"我不知道"，不强凑方案
- 用户原话："你不能丢一大堆都不靠谱的方案让我选吧"

### 5. 数据原则

- **可以跑 30 局做归因**（明确目的，不是 sweep）
- **禁止用脏数据 warm start**（脏数据让 model 学到错老师 bias，反而拖累）
- 脏数据 = 之前错老师源（v8_strategy 启发式）跑出来的产物，所有 `archive/v8_bc_pivot/data/` 下的都是脏的
- 用户原话："不要用已有的数据，看起来都是脏数据"

### 6. 心态原则

- **机器学习没把握很正常**——不要道歉"我没把握"
- **不要焦虑 / 绝望 / 沮丧** —— reframe 为 productive
- 50% 失败概率 = 50% 成功概率
- 失败也学到东西（知道这条路不行 → 下一步换什么）
- 用户原话："你看起来很绝望，对此不抱有任何希望能完成... 不要焦虑和绝望，我们有正确的方法论"

### 7. 指令理解后输出确认再执行

- 收到任何技术性指令必须先**复述理解**等用户确认后再执行
- 复述要包含：(1) 理解的目标 (2) 具体要做的事 (3) 不做的事
- 用户原话："后续我的所有指令你理解之后要输出之后再执行"
- 简单事务（"check 进度"、"看下结果"）可以直接做

### 8. 听用户原话精读关键词

- 不要用 ML 术语硬套用户人话
- 用户用具体名词时（"老师"、"辅助"、"评分"），精读语义指代
- 历史教训：把用户"老师 = 搜索"误读成"老师 = 启发式"，绕路 7-8 小时

## 历史教训

- "老师"≠ 启发式 v8_strategy，**"老师" = StSRLSolver 战斗搜索**
- 任何用人写规则做 BC teacher 的设计都已被验证撞天花板（0/30 beat boss）
- 单 reward 反推（`game_won` only）在 0 winning data 起点冷启动死结
- 分层评估（每个子决策懂行信号）才是用户最早的设计意图
- Claude 倾向"找 cheap 替代避开大工程"——避开正确路径反而绕路 7-8 小时
- Claude 倾向"列方案让用户拍"——把决策外包，违反"按方法论稳定推进"
